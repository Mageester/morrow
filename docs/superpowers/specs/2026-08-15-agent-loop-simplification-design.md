# Agent loop simplification design

Date: 2026-08-15

## Goal

Replace Morrow's behavior-supervising execution path with a small provider-neutral
model → tool → result loop while preserving durable missions, resumability,
approvals, Mission Guardian, provider portability, memory boundaries, explicit
budgets, cancellation, and evidence-backed completion.

The current uncommitted working tree is the approved baseline. Its provider-owned
capability, canonical request/context, typed provider error, and stream
normalization work must remain intact. Unrelated UI and CLI edits are protected.

## Evidence

`services/orchestrator/src/execution/agent.ts` currently owns the ordinary agent
loop plus progress epochs, exact-call loop detection, convergence accounting,
generic stagnation state, post-delivery read allowances, action-only recovery,
artifact-delivery termination, forced tool-choice recovery, completion-contract
recovery, and mission-worker strategy escalation. Several of these mechanisms
decide whether the model is acting or reasoning correctly rather than protecting
the user, computer, provider, or durable record.

The official `deepseek-ai/deepseek-harness` implementation at commit `47f9438`
keeps `ReactLoopAgent.step()` mechanical: derive the request from the session
log, stream and persist one assistant message, execute requested tools, persist
their results, and repeat. Its repeat-tool reminder is a separate advisory hook;
it neither vetoes the tool nor interrupts the mission. Its reconstruction tests
enforce that every model-visible input is derivable from the durable log.

## Normal execution path

The ordinary path is:

1. Claim the current task input or resumed execution lease.
2. Reconstruct the model-visible request from durable provider turns, tool
   results, checkpoints, permitted memory, and the current system/tool surface.
3. Resolve the exact provider adapter and its route capabilities.
4. Admit the canonical request against the route-aware context limit.
5. Stream the normalized provider response and persist the assistant turn.
6. If the response requests tools, validate and execute them through the
   existing permission, containment, cancellation, and replay-safety boundaries.
7. Persist each tool result before the next provider request.
8. Repeat from reconstruction while tool calls create more work.
9. When the provider returns a tool-free completion candidate, evaluate objective
   completion evidence through the existing Mission Guardian/finalization path.

No parallel loop or replacement orchestration framework is introduced.

## Delete from the hot path

- Progress epochs and observation-exhaustion policing.
- Generic no-progress/stagnation counters and post-delivery read allowances.
- Convergence guards that pause the whole mission for repeated writes.
- Mission-worker `strategy_change_required` escalation caused by model behavior.
- Forced strategy changes or automatic pauses requiring the user to continue.
- Global repeated-read/write rejection or cached-observation substitution whose
  purpose is controlling the model rather than enforcing replay safety.
- Repeated generic progress-warning events generated by those systems.
- Artifact-delivery turn thresholds and trusted fresh-context resets that attempt
  to repair the model's reasoning by replacing its visible history.
- Duplicate recovery layers where typed provider retry, context compaction,
  cancellation, or durable resume already owns the failure.

Deletion includes obsolete tests and the accepted ADR that requires mission-level
convergence interruption. No deleted mechanism may be retained behind a flag,
renamed, or moved into another generic controller.

## Advisory repeat handling

Exact tool-call identity is the tool name plus canonicalized arguments. Advisory
state is task-local and never grants authority to execute a tool.

- On the third identical call, append a durable, model-visible reminder that the
  exact call is repeating and the previous result should be inspected.
- On later configured reminder points, include the prior result or its existing
  durable artifact reference and ask the model to choose a different action or
  finish if the evidence is sufficient.
- Do not pause the task, fail a segment, force a strategy, or reject ordinary
  reads/writes because of repetition.
- A narrow exact-action rejection is permitted only for an objectively
  pathological unbounded action and must not interrupt unrelated task work. This
  rejection is not required for the initial simplification unless live evidence
  proves advisory handling cannot bound resource use under an explicit budget.

The reminder must be provider-neutral and must not name Qwen, DeepSeek, GPT,
Claude, Gemini, or any model family.

## Model-visible durable history

`buildProviderProjection` and the durable execution-continuity repositories remain
the authoritative story. After a successful tool call, the next canonical request
must contain the assistant tool request and its exact successful result once, in
valid provider ordering. A successful `create_file` result must remain visible as
success; it must not be replaced by an executable replay marker, a contradictory
mission-state narrative, or a hidden transient cache.

Private provider continuation may remain outside the public event projection but
must stay route-bound and durably reconstructable at its existing restricted
boundary. Canonical request/context/stream work already present in the baseline is
preserved.

## Hard enforcement retained

Hard enforcement remains only where it protects an objective invariant:

- Permission and approval decisions.
- Workspace/path containment and secret/privacy boundaries.
- Tool schema and argument validity.
- Duplicate side-effect protection caused by orchestrator replay or retry.
- Exact provider protocol/capability and hard context/output limits.
- Cooperative cancellation and process cleanup.
- Bounded transport/provider retry before useful output commits.
- Durable writes, execution leases, checkpoints, restart recovery, and ordering.
- Explicit user-configured time, token, cost, turn, and tool budgets.
- Mission Guardian requirements and evidence-backed completion.

Malformed tool arguments may return a structured error for the model to correct.
They must not trigger a generic strategy supervisor. Provider-specific code is
allowed only for actual wire protocol or capability differences.

## Failure behavior

- A tool denial, invalid argument, tool failure, or verification failure is
  persisted as a tool result and returned to the model when safe to continue.
- Cancellation stops new work, drains or records in-flight work according to its
  existing ownership rules, and persists the truthful terminal state.
- Context overflow uses the typed, bounded compaction/retry path already present.
- Provider failure uses bounded adapter/fallback policy and never retries after
  useful output when doing so could duplicate a side effect.
- Mission Guardian may reject unsupported completion, but it does not judge the
  model's reasoning style or tool sequence.

## Verification

Deterministic tests must prove:

1. Repeated identical reads and writes remain executable and do not interrupt the
   task or produce `loop_stalled`, `no_progress`, or strategy-change outcomes.
2. The third exact call adds a durable model-visible advisory and continued calls
   receive stronger context without global interruption.
3. Successful tool results are visible exactly once in the immediately following
   canonical provider request, including after restart and segment rollover.
4. Permission, containment, invalid-argument, replay-idempotency, cancellation,
   explicit-budget, context-limit, and Guardian failures remain hard.
5. Existing provider capability, canonical request, context budget, error, stream,
   and cross-model conformance tests remain green.

After deterministic verification, start the real Morrow UI and run the exact
configured Qwen task unchanged:

> Finish this website. Inspect what already exists, fix everything necessary,
> create any missing assets, verify the result actually works, and do not stop
> until the site is complete.

Observe the real Activity stream and durable events. A healthy run may be messy,
but ordinary imperfect behavior must not become warning → warning → global loop
detector → mission interruption. If Morrow still fights the model, simplify the
root cause; do not raise thresholds or hide warnings. After Qwen, run the same
task unchanged on other configured real models, serialized to avoid shared
workspace/process interference.

## Required final evidence

The handoff must show the behavioral-control machinery that existed, what was
deleted, what became advisory, what hard enforcement remains and why, the normal
path size before and after, deterministic commands/results, and real UI results
for Qwen and each other configured model. Record privacy/security impact and
rollback notes. Do not claim live success from scripted or unit-only providers.
