## D4 — `installer --version X` installs a different version and reports success

**Severity:** Medium. Produces false completion evidence. Latent while the public
manifest is current; user-visible whenever it is not.

**Reproduction** (observed while the public manifest still advertised 0.7.0):

```
sh install.sh --version 0.7.1 --prefix ./iso/app --bin-dir ./iso/bin --no-start
```

**Observed** — note the self-contradiction in its own output:

```
Downloading Morrow 0.7.1 (Morrow-v0.7.0-linux-x64.tar.gz, ~91 MB)...
Verifying SHA-256 checksum...
Checksum verified. Extracting...
Morrow 0.7.1 installed to .../iso/app
```

Installed reality: `morrow --version` → **0.7.0**; `PROVENANCE.json` →
`sourceCommit 857f602`, `schemaCatalogVersion 67`. **Exit code 0.**

**Root cause** — `installer/install.sh`:

```sh
542:  version="$(json_string "$manifest" version)"
543:  [ -n "$WANT_VERSION" ] && version="$WANT_VERSION"          # overrides the LABEL only
546:  [ -n "$WANT_VERSION" ] && [ "$WANT_VERSION" != "$(json_string "$manifest" version)" ] && commit=""
550:  artifact="$(manifest_artifact "$manifest" "$platform")"    # still the STALE artifact
```

Line 543 overrides only the display label; line 550 still selects the artifact
from the manifest. Line 546 is the damning part — the script **detects** the
mismatch and responds by blanking `commit`, disabling provenance verification
rather than failing. "Checksum verified" is true and meaningless: it verified
0.7.0 against the 0.7.0 entry.

Pre-existing — v0.7.0's `install.sh` is byte-identical
(`sha256 5551d3e698b594df79241ce66654f352abf8bb1d60e663657f88b59152fd1b2c`).

**Fix:** if `WANT_VERSION` is set and differs from the manifest version, fetch
that version's own manifest or hard-fail. Never install one version while
labelling it another.

## D5 — `--model` without `--provider` routes to the wrong provider

**Severity:** Low-Medium. Confusing failure on a model discovery reports available.

```
morrow ask --message "…" --model x-preview-f-free
→ The supported API model names are deepseek-v4-pro, deepseek-v4-flash, and
  deepseek-v4-flash-vision-exp, but you passed x-preview-f-free.
```

Same for `qwen/qwen3.8-max-free` (tokenrouter) and `01-ai/yi-large` (nvidia-nim).
All three were sent to **deepseek**, the preset's provider. Adding `--provider`
works: opencode-zen/`x-preview-f-free`, tokenrouter/`qwen3.8-max-free`, and
deepseek/`deepseek-v4-flash` all completed.

`morrow models` lists each model *with its provider column*, so `--model <id>`
reasonably reads as sufficient. The error names the wrong provider's model list
and never mentions `--provider`.

**Fix:** when `--model` is given without `--provider` and the id resolves to
exactly one provider in the catalogue, either select that provider or fail with
"model `X` belongs to provider `Y`; pass `--provider Y`."

## D6 — Provider discovery lists models that 404 on use

**Severity:** Low-Medium.

Discovery reports 95 nvidia-nim models as `●` provider-reported/available:

| model | result |
|---|---|
| `meta/llama-3.1-8b-instruct` | works — executed 37 tools over 52.5s |
| `01-ai/yi-large` | `404 Not Found … for account` |
| `mistralai/mistral-7b-instruct-v0.3` | `404 Not Found … for account` |

The provider works; a significant fraction of advertised models do not exist for
the account. `morrow models` states "Only models proven available for this
account are shown", which is not what is happening for nvidia-nim.

**Fix:** verify per-model availability for this provider class, or soften the
wording so "provider-reported" is not presented as proven for the account.

## D7 — Composer shows the same model name twice

**Severity:** Low, cosmetic.

The toolbar renders the model in two adjacent controls: `ModelPicker`
(`x-preview-f-free`) and the `CapabilityStatus` trigger
(`OpenCode Zen · x-preview-f-free`), with nothing indicating they differ.

`apps/web/src/features/chat/capability-status.tsx:156` builds the trigger label
unconditionally. The component already computes what it needs to avoid this:

```ts
const routeChangedSinceLastTurn = Boolean(
  liveProvider && configuredProvider && (liveProvider !== configuredProvider || liveModel !== configuredModel),
);
```

…but consults it only inside the expanded panel (line 209), never to collapse the
trigger. So the genuinely useful signal — *the model that ran is not the one in
the picker* — looks identical to every other case.

Introduced by `5bc7ff9` (perf PR #76), an ancestor of v0.7.0.

**Fix:** gate the trigger label on the existing flag. When
`!routeChangedSinceLastTurn`, drop the model from the trigger and keep the
provider or the ring alone. Show full `provider · model` only when it diverges —
turning redundancy into the alert it was meant to be.

## Resolved during validation (recorded for the record)

**Manifest propagation.** For ~20 minutes after the tag, the public endpoint
still served `0.7.0` while GitHub had `0.7.1`. Not a CDN artifact —
`cf-cache-status: DYNAMIC`, `max-age=0, must-revalidate`, so the origin was
stale. `release.yml` ends at *Create GitHub Release* and uploads `latest.json`
only as a release asset; the site deploy is out-of-band. It completed
subsequently. Live manifest now reports `0.7.1`, commit `4eab424`, and all 5
platform checksums match the published checksums file.

Minor inconsistency: the deployed `latest.json` carries `commit` and `source`
provenance fields that the GitHub release asset omits.

**Verify Public Install Contract is a permanently-red alarm.** Failed on every
scheduled run for 25+ consecutive runs:
`GET https://morrowproject.getaxiom.ca/releases/latest.json -> 403 Forbidden`
from GitHub runners. IP/WAF blocking of datacenter ranges, not user-agent — the
same URL returns 200 from a normal host across six different UAs. Not
release-blocking, but it is the one workflow whose job is detecting a broken
public install, so a real breakage is currently indistinguishable from the
standing failure. This is exactly what would have caught the manifest gap above.
Prior art: the install commands were once silently broken for 12 days.

**Not a defect: task "completed" with an earlier "failed" event.** A support
bundle showed task `e1de89a3` recorded `completed` while carrying a `Task failed`
system event. The failed event at sequence 233 is not terminal — events continue
through 415. The task hit a mid-run failure, recovered, and genuinely completed.
Filtering to `system`-kind events alone makes this look like a contradiction.

## Process note

Multiple agent sessions were committing into `/home/dread/Code/morrow` during the
live release. It caused two false conclusions in one hour: a source read against
a HEAD that moved mid-analysis, and an authorship inference from reflog. `reflog`
is per-checkout and attributes nothing, and every session commits under the same
git identity, so authorship cannot be established from inside a shared tree. Use
`git worktree add` for concurrent sessions.
