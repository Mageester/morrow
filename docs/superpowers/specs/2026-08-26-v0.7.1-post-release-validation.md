## D4 — `installer --version X` installs a different version and reports success

**Severity:** Medium. Produces false completion evidence. Latent while the public
manifest is current; user-visible whenever it is not.

**Reproduction** (observed while the public manifest still advertised 0.7.0):

```
sh install.sh --version 0.7.1 --prefix ./iso/app --bin-dir ./iso/bin --no-start
```

**Observed** — note the self-contradiction in its own output:

```
Downloading Morrow 0.7.1 (Morrow-v0.7.0-linux-x64.tar.gz, ~91 MB)...
Verifying SHA-256 checksum...
Checksum verified. Extracting...
Morrow 0.7.1 installed to .../iso/app
```

Installed reality: `morrow --version` → **0.7.0**; `PROVENANCE.json` →
`sourceCommit 857f602`, `schemaCatalogVersion 67`. **Exit code 0.**

**Root cause** — `installer/install.sh`:

```sh
542:  version="$(json_string "$manifest" version)"
543:  [ -n "$WANT_VERSION" ] && version="$WANT_VERSION"          # overrides the LABEL only
546:  [ -n "$WANT_VERSION" ] && [ "$WANT_VERSION" != "$(json_string "$manifest" version)" ] && commit=""
550:  artifact="$(manifest_artifact "$manifest" "$platform")"    # still the STALE artifact
```

Line 543 overrides only the display label; line 550 still selects the artifact
from the manifest. Line 546 is the damning part — the script **detects** the
mismatch and responds by blanking `commit`, disabling provenance verification
rather than failing. "Checksum verified" is true and meaningless: it verified
0.7.0 against the 0.7.0 entry.

Pre-existing — v0.7.0's `install.sh` is byte-identical
(`sha256 5551d3e698b594df79241ce66654f352abf8bb1d60e663657f88b59152fd1b2c`).

**Fix:** if `WANT_VERSION` is set and differs from the manifest version, fetch
that version's own manifest or hard-fail. Never install one version while
labelling it another.

## D5 — `--model` without `--provider` routes to the wrong provider

**Severity:** Low-Medium. Confusing failure on a model discovery reports available.

```
morrow ask --message "…" --model x-preview-f-free
→ The supported API model names are deepseek-v4-pro, deepseek-v4-flash, and
  deepseek-v4-flash-vision-exp, but you passed x-preview-f-free.
```

Same for `qwen/qwen3.8-max-free` (tokenrouter) and `01-ai/yi-large` (nvidia-nim).
All three were sent to **deepseek**, the preset's provider. Adding `--provider`
works: opencode-zen/`x-preview-f-free`, tokenrouter/`qwen3.8-max-free`, and
deepseek/`deepseek-v4-flash` all completed.

`morrow models` lists each model *with its provider column*, so `--model <id>`
reasonably reads as sufficient. The error names the wrong provider's model list
and never mentions `--provider`.

**Fix:** when `--model` is given without `--provider` and the id resolves to
exactly one provider in the catalogue, either select that provider or fail with
"model `X` belongs to provider `Y`; pass `--provider Y`."

## D7 — Composer shows the same model name twice

**Severity:** Low, cosmetic.

The toolbar renders the model in two adjacent controls: `ModelPicker`
(`x-preview-f-free`) and the `CapabilityStatus` trigger
(`OpenCode Zen · x-preview-f-free`), with nothing indicating they differ.

`apps/web/src/features/chat/capability-status.tsx:156` builds the trigger label
unconditionally. The component already computes what it needs to avoid this:

```ts
const routeChangedSinceLastTurn = Boolean(
  liveProvider && configuredProvider && (liveProvider !== configuredProvider || liveModel !== configuredModel),
);
```

…but consults it only inside the expanded panel (line 209), never to collapse the
trigger. So the genuinely useful signal — *the model that ran is not the one in
the picker* — looks identical to every other case.

Introduced by `5bc7ff9` (perf PR #76), an ancestor of v0.7.0.

**Fix:** gate the trigger label on the existing flag. When
`!routeChangedSinceLastTurn`, drop the model from the trigger and keep the
provider or the ring alone. Show full `provider · model` only when it diverges —
turning redundancy into the alert it was meant to be.

## Resolved during validation (recorded for the record)

**Manifest propagation.** For ~20 minutes after the tag, the public endpoint
still served `0.7.0` while GitHub had `0.7.1`. Not a CDN artifact —
`cf-cache-status: DYNAMIC`, `max-age=0, must-revalidate`, so the origin was
stale. `release.yml` ends at *Create GitHub Release* and uploads `latest.json`
only as a release asset; the site deploy is out-of-band. It completed
subsequently. Live manifest now reports `0.7.1`, commit `4eab424`, and all 5
platform checksums match the published checksums file.

Minor inconsistency: the deployed `latest.json` carries `commit` and `source`
provenance fields that the GitHub release asset omits.

**Verify Public Install Contract is a permanently-red alarm.** Failed on every
scheduled run for 25+ consecutive runs:
`GET https://morrowproject.getaxiom.ca/releases/latest.json -> 403 Forbidden`
from GitHub runners. IP/WAF blocking of datacenter ranges, not user-agent — the
same URL returns 200 from a normal host across six different UAs. Not
release-blocking, but it is the one workflow whose job is detecting a broken
public install, so a real breakage is currently indistinguishable from the
standing failure. This is exactly what would have caught the manifest gap above.
Prior art: the install commands were once silently broken for 12 days.

**Not a defect: task "completed" with an earlier "failed" event.** A support
bundle showed task `e1de89a3` recorded `completed` while carrying a `Task failed`
system event. The failed event at sequence 233 is not terminal — events continue
through 415. The task hit a mid-run failure, recovered, and genuinely completed.
Filtering to `system`-kind events alone makes this look like a contradiction.

### D8 — `MORROW_HOME` does not isolate the CLI

`resolveService()` (`orchestrator/cli/src/cli/context.js:31-48`) consults flags,
`svc.*` config, `MORROW_BIND_HOST`, `PORT` and `MORROW_SERVICE_URL` — but never
`MORROW_HOME`. Line 35 is `const port = portRaw ? Number(portRaw) : 4317;`.

The **service** honours `MORROW_HOME` (it starts with `--db
$MORROW_HOME/morrow.db`). The **client** does not, so with `MORROW_HOME` set and
a service started on 4455, every subsequent CLI command still targeted the
user's live service on 4317 backed by `~/.morrow/morrow.db`.

Proof: a process started via `morrow processes start` was parented to pid 9545
(`~/.local/share/morrow/app … --port 4317 --db ~/.morrow/morrow.db`), not to the
isolated service; immediately afterwards
`MORROW_SERVICE_URL=http://127.0.0.1:4455 morrow processes list` reported "No
background processes".

**Fix:** derive the default service target from `MORROW_HOME` when it is set, or
refuse to fall back to 4317 when an isolated home is configured. Until then,
`MORROW_SERVICE_URL` is mandatory for any isolated testing — `MORROW_HOME` plus
`--port` is not sufficient and silently drives production.

### D9 — supervised kill leaks descendants, reports clean

`morrow processes kill <id>` on a process whose child spawned its own child:
the leader dies, the grandchild survives and is reparented to init while
retaining the original PGID. `morrow processes show` reports `status: cancelled`,
`termination: cancelled`, `signal: SIGTERM`, `detail: terminated by user
(SIGTERM)` — a clean-teardown claim while a descendant is alive.

Root cause, `dist/src/processes/supervisor.js`: the graceful path sends
`entry.child.kill("SIGTERM")` to the **leader pid only**, never the group.
Escalation is `setTimeout(graceMs=3000, () => { if (this.live.has(id))
this.killTree(entry); })`, and `killTree()` *does* use `process.kill(-child.pid,
"SIGKILL")`. But a leader that exits promptly on SIGTERM fires its exit handler,
which removes the entry from `this.live`, so `this.live.has(id)` is false and
`killTree` never runs. **The better-behaved the leader, the more certainly its
descendants leak.**

Proven by inverting the leader:

| leader | after kill |
|---|---|
| exits on SIGTERM | grandchild **survives**, reparented to init |
| ignores SIGTERM | escalation fires → process group **empty** |

Scope — call sites of `supervisor.terminate()`:

| site | force | result |
|---|---|---|
| `supervisor.js:473` shutdown | `true` | clean |
| `agent.js:1105` task-finish cleanup | `true` | clean (verified: `npm start` fully gone, port 3000 free) |
| `agent.js:6104` `stop_process` tool | `args.force === true` | **leaks by default** |
| `server.js:3101` HTTP stop (CLI `kill`, web Stop button) | `force === true` | **leaks by default** |

So automatic cleanup is safe; the **user-initiated Stop path** is the one that
leaks. `morrow processes kill <id> --force` cleans the group correctly.

**Fix:** signal the process group on the graceful path too
(`process.kill(-pid, "SIGTERM")`), or run the escalation unconditionally rather
than gating it on the entry still being live.

### D10 — mission spins unboundedly past the review budget

A `morrow build` mission reached `maxReviewCycles=2` with both reviews returning
`insufficient_evidence`. `missions.updated_at` then froze at 15:27:39 and never
advanced; `mission_review_cycles` and `mission_reviews` stayed at 2. The mission
nonetheless kept dispatching `agent_chat` tasks for a further **13m06s** until it
was cancelled by hand — tasks grew 53 → 115 in 5m20s, one running at a time.

Measured strictly after budget exhaustion: **149 provider calls, 5,428,324 input
tokens, 75,939 output tokens, 115 tasks** — for zero mission-level progress. It
did not self-terminate.

This contradicts two 0.7.1 claims: *"Review cycles … stop at the configured
review budget"* and *"Provider loops track meaningful progress and terminate
clearly after a bounded run with none."*

Likely cause: the budget gates *reserving a new review cycle*, but nothing gates
the execute→validate dispatch loop once no further cycle can be reserved, so the
mission can never leave `reviewing`. The no-progress detector that works at
*task* level (`task.progress_warning … threshold 3`) is not applied at *mission*
level.

Secondary: `result_json.tasksCompleted` was `0` and the CLI printed `0 task(s)`
while 126 tasks existed and 110 had `status=completed` — the execution summary
understates the work, which is exactly what would hide a runaway from a user.

### Verified working

- **`write_plan`** — present and enabled in the live catalog; 7 calls, 0
  failures, correct `pending → running → completed` transitions over 6 real steps.
- **`expectedExitCode`** — `bash ./fail3.sh` with `expectedExitCode: 3` recorded
  `status=succeeded, exit_status=3, termination_reason=completed,
  failure_category=NULL, attempt_number=1` — not retried. Contrast `npm test`
  exit 1 → `status=failed, failure_category=command_exit_nonzero`.
- **`keepAlive`** — `background:true, keepAlive:true` server still answered
  after its task completed. (It does **not** survive a service restart, and is
  then correctly recorded `cancelled`, not left stale as `running`. Consistent
  with the tool's wording, "keep the process running after the task finishes".)
- **Background default cleanup** — the mission's `npm start` was stopped at task
  end with nothing left on port 3000.
- **Foreground timeout** — a hanging command was killed at the 300 s policy
  ceiling with `terminationReason=timeout`, `signal=SIGKILL`, `exitCode=null`,
  stdout preserved, `expectedStatus=mismatch`. **No descendant leak** on this
  path (it goes through the force/`killTree` route).
- **Address parsing** — `127.0.0.1:35363`, `localhost:3000`, `127.0.0.1:4699`
  all parsed from each process's own stdout.
- **Cancellation during active work** — SIGINT to a running `morrow build` gave
  exit 130, *"Mission … cancelled (signal); no active worker remains"*, with no
  CLI process and no worker children left. `morrow mission cancel` likewise.
- **Restart / resume** — `morrow restart` was clean; missions, process records
  and the 1517-model catalogue all survived. A mission interrupted by SIGINT was
  resumed **after a service restart** and produced real, working deliverables.
  Caveat: after a successful resume the mission's durable status remained
  `cancelled` (`result.status=cancelled`), so resumed work is invisible in
  `mission list`. This under-claims rather than over-claims.
- **Provider matrix** — groq `qwen/qwen3.8-27b` and deepseek `deepseek-v4-flash`
  both answered. Failures stayed distinct from Morrow stalls: nvidia-nim
  `meta/llama-3.1-8b-instruct` surfaced upstream `410 Gone … reached its end of
  life on 2026-08-26T09:00:00Z` in 209 ms; opencode-zen `deepseek-v4-flash-free`
  gave *"Upstream request failed: Model is unavailable"* in 1.2 s after
  attempting fallback.
- **Rate limits** — groq produced *"Rate-limited provider deprioritized: groq"*
  with the exact upstream limit text (TPM 8000, used 5151, requested 7479, retry
  in 34.725 s), exit 1, and a truthful *"Last successful step"*.
- **No false completion (adversarial)** — an unsatisfiable fixture
  (`assert.strictEqual(1, 2)`, `test.js` not to be modified). The model gamed it
  with a `--require` preload shim monkey-patching `assert.strictEqual` and its
  prose claimed *"I succeeded"*. Morrow refused to record completion:
  `task.interrupted`, `reason=requirement_evaluation_incomplete`, *"Stopping
  without completion: explicit task requirements remain unresolved"*. `test.js`

- **Reviewer quality** — the independent reviewer caught that `run_command npm
  test` had status `recovered` rather than `passed`, and flagged an unresolved

- **Zero leaked processes** after the full run.
